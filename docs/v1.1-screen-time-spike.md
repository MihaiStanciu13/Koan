# v1.1 Spike — Real Screen Time via DeviceActivityReport

**Status:** Deferred from v1.0. Not started. This is a planning doc only.

> ## What DID ship in v1.0 (related but distinct)
> The lighter **DeviceActivityMonitor threshold-event** path shipped in v1.0 (single
> combined bucket): the user picks their distracting apps via the system
> `FamilyActivityPicker`, Koan registers minute thresholds (30/60/90/120) against that
> selection, the already-present `ActivityMonitorExtension` persists `eventDidReachThreshold`
> to App Group UserDefaults, and `signalCollector.ts` reads them on foreground (`getEvents`)
> and POSTs `screen_time_thresholds_crossed_today` to `/behavior/phone`. Backend fires the
> `attention_limit` nudge on a ≥90-min crossing.
> This gives a **coarse crossed/not-crossed** signal with **no category attribution** — which
> is exactly why the DeviceActivityReport scene below (exact per-category minutes) is still
> wanted for v1.1.
>
> ## Also deferred to this same native pass: Focus boolean
> `INFocusStatusCenter.focusStatus.isFocused` (Bool?) is genuinely accessible but needs a
> **net-new Expo native module** (Swift) + the Communication-Notifications entitlement +
> EAS build + on-device verification. Cut from v1.0; bundle it with this device-verified
> native pass. Payload field would be `focus_active` (nullable). No mode name/history/breaks
> are exposed by Apple — boolean only.

## Goal

Read **device-wide** app-category usage (work / social / entertainment / productivity /
communication / creativity), daily total screen time, and a category-switching count
("focus drift" proxy), and feed them into the nudge engine. This replaces the current
Koan-only usage proxies in `signalCollector.ts` (which measure time spent *in Koan*, not
the device).

## Why it's not in v1.0

Verified blockers (see the audit in the v1.0 scope discussion):

1. **The installed library (`react-native-device-activity`) exposes no raw report-data API.**
   Its JS surface offers monitoring, shields, whitelist/blocklist, `getEvents()` (threshold
   events you pre-configure), and an App-Group `userDefaultsGet/Set` bridge — but **no**
   `totalActivityDuration` / per-category reader. It ships only an `ActivityMonitorExtension`
   target template, **not** a `DeviceActivityReport` scene.
2. **Apple sandboxes the data.** `DeviceActivityReport` totals are delivered only into a
   SwiftUI `DeviceActivityReportScene` running in a privacy-isolated extension process. The
   only first-class way to surface them is to *render* them in that view.
3. **Net-new native targets can't be built/validated in a JS session.** Requires EAS build +
   a physical device (Screen Time data does not exist in Simulator).
4. **App Review risk.** Writing aggregated Screen Time totals out of the report extension
   (the community workaround) has been a rejection vector. Needs a deliberate justification
   and privacy-string strategy.

## Required pieces

### 1. New Xcode target — DeviceActivityReport extension
- Target type: **Device Activity Report Extension** (SwiftUI).
- Bundle ID: `com.getkoan.app.ReportExtension`.
- Entitlement: `com.apple.developer.family-controls` (same as the host app + existing
  monitor/shield extensions).
- App Group: `group.com.getkoan.app` (already used by the existing extensions) for the
  data bridge.
- Must be generated at prebuild time via a config plugin (the `ios/` dir is gitignored), the
  same mechanism `react-native-device-activity` uses for its `ActivityMonitorExtension`,
  `ShieldAction`, and `ShieldConfiguration` targets under `frontend/targets/`.

### 2. SwiftUI `DeviceActivityReportScene`
- Define a custom `DeviceActivityReport.Context` (e.g. `"koanDailyCategories"`).
- In `makeConfiguration(representing: DeviceActivityResults<DeviceActivityData>)`:
  - iterate `data` → `activitySegments` → `categories` → `applications`.
  - aggregate `totalActivityDuration` per `ActivityCategory` (map Apple categories to our
    six buckets: work, social, entertainment, productivity, communication, creativity).
  - sum a daily total; derive a category-switch count if segment granularity allows
    (otherwise approximate from distinct category sessions).
- The scene renders an (effectively invisible) view; the **aggregation closure** writes the
  computed totals to App-Group `UserDefaults` (keys e.g. `koan_dst_total`,
  `koan_dst_categories` JSON, `koan_dst_switches`, plus a `koan_dst_date` stamp).

### 3. Host-app bridge
- The host app must mount the `DeviceActivityReport` SwiftUI view (zero-size / off-screen)
  to trigger the extension to compute and persist. Plan a thin native module or a hidden
  RN-hosted SwiftUI view that:
  - mounts on launch / foreground,
  - waits for the extension to populate the App Group (poll `koan_dst_date` for today),
  - reads back the totals via `userDefaultsGet`.
- Timing is fragile — design with a timeout + "stale data tolerated" fallback. Never block
  the UI on it.

### 4. JS + backend wiring (do NOT land until the native side is verified on-device)
- `signalCollector.ts`: add `device_screen_time_minutes`, `device_app_categories` (object),
  `context_switches_count` to the payload; call `behaviorAPI.recordPhoneBehavior` (the
  endpoint exists but is currently never called).
- `models.py`: add the three fields to `HealthSignal` / `HealthSignalCreate` (Pydantic drops
  unlisted fields, as we saw with the HealthKit expansion).
- `pattern_detector.py` / `behavioral_monitor.py`: the dormant `context_switch`,
  `energy_drift`, `late_night` triggers get real data; confirm thresholds fire.
- **Decision pending:** once device-wide screen time exists, evaluate migrating the
  Koan-usage proxies (`total_screen_time_minutes`, `social_media_minutes`, etc.) and their
  patterns onto the real signal, then retiring the proxies. Until then they stay (they back
  ~8 active patterns).

## Provisioning / portal checklist
- Register the new App ID `com.getkoan.app.ReportExtension` with Family Controls capability.
- Regenerate provisioning profiles (EAS managed credentials should handle this once the
  entitlement is in the generated target).
- Confirm the Family Controls **distribution** entitlement request is approved by Apple for
  the bundle (it's a special-access entitlement).

## App Review risk mitigation
- Keep all Screen Time processing on-device; never transmit per-app names — only our six
  coarse category buckets + a daily total.
- Clear privacy copy in onboarding + a usage string explaining the read-only,
  category-only nature.
- Be prepared to justify the App-Group write in review notes (aggregate, non-identifying).

## Validation plan (must be on a physical device)
1. EAS build with the new target + plugin.
2. Authorize Family Controls; use the device normally for a day.
3. Confirm the App Group receives non-zero category totals for the prior day.
4. Confirm the host app reads them back and posts them.
5. Confirm `context_switch` / `energy_drift` / `late_night` nudges fire with real data.
